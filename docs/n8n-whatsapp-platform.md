# Platform webhook → n8n → Evolution API

This integration starts disabled. Do not activate the platform webhook until the database migration, n8n workflow, credentials, and test recipients are ready.

## rOndevu configuration

Set these secrets in the deployment manager, never in Git:

- `PLATFORM_N8N_WEBHOOK_URL`: exact n8n **production** webhook URL.
- `PLATFORM_N8N_ALLOW_PRIVATE_HTTP=1`: only when n8n is reached over a private Docker network. Otherwise use HTTPS.
- `RONDEVU_N8N_INGRESS_KEY`: random 32+ byte secret; configure as the n8n Webhook node's Header Auth credential for `X-Rondevu-Ingress-Key`.
- `RONDEVU_N8N_ELIGIBILITY_TOKEN`: different random 32+ byte secret; n8n uses it as `Authorization: Bearer ...` for the eligibility and opt-out endpoints.
- `RONDEVU_WEBHOOK_REPLAY_KEY`: independent 32 random bytes, Base64 encoded; encrypts failed platform delivery bodies for administrator retry.
- `RONDEVU_PLATFORM_WEBHOOK_ENABLE=1`: deployment gate to permit activation after the checks below. New platform webhooks are always created inactive.

The deployment gate and the webhook's active flag are both checked when queued jobs run. Deactivating the webhook stops queued platform sends that have not executed yet.

Apply `20261027000000_platform_whatsapp_webhook` before deploying the application. In `/settings/developer/webhooks`, an administrator creates a **Platform** webhook with the exact configured URL, a new random HMAC secret, all supported triggers, and `active=false`. Activate it only after the checks below. The HMAC secret belongs in n8n Crypto credentials and must differ from the ingress and eligibility secrets. Existing user webhooks remain separate.

## Dokploy prerequisites

Run n8n as a separate persistent service with its own database and encryption key. The Evolution API deployment needs a nonempty PostgreSQL `POSTGRES_PASSWORD`, a matching `DATABASE_CONNECTION_URI`, and an independent `AUTHENTICATION_API_KEY`; keep these values in Dokploy secrets. Do not use PostgreSQL trust authentication. Confirm both services are healthy before adding a production webhook URL. The local Docker Desktop installation uses the named `dokploy-config` volume for `/etc/dokploy` so its configuration survives a restart; include that volume in backups.

For the existing Evolution Compose service, set at least `POSTGRES_DATABASE`, `POSTGRES_USERNAME`, `POSTGRES_PASSWORD`, `DATABASE_PROVIDER=postgresql`, `DATABASE_CONNECTION_URI=postgresql://<user>:<URL-encoded-password>@evolution-postgres:5432/<database>`, `DATABASE_ENABLED=true`, `AUTHENTICATION_API_KEY`, and `SERVER_URL` to its actual HTTPS hostname. Use a different secret for each service. Its Redis URI is `redis://evolution-redis:6379`. The Compose mapping is `8080:8080`; a host-network Cloudflare Tunnel can reach `http://localhost:8080` only after Evolution is healthy. Bind the host side to `127.0.0.1:8080` if the Tunnel is the sole intended public route, and map the intended hostname to that origin in Cloudflare. Dokploy's autogenerated `sslip.io` domain does not create a Cloudflare Tunnel route.

The current n8n Compose definition is deployed with nonempty PostgreSQL credentials, a persistent `N8N_ENCRYPTION_KEY`, and a pinned image version. It binds only to local port 5678 and shares `dokploy-network` with rOndevu. If the editor is later published behind HTTPS, set `N8N_SECURE_COOKIE=true` and update `WEBHOOK_URL` to that HTTPS address. Keep the editor behind authentication; the public webhook path alone does not need editor access. Do not expose its PostgreSQL port publicly.

The task queue is separate from immediate Twilio SMS dispatch. Schedule authenticated `GET /api/tasks/cron` once per minute with `CRON_API_KEY`. Review existing due tasks before first activation. Booking reminder jobs now skip bookings that have already started, so overdue reminders are not sent after the appointment. Do not log queued task payloads because they can contain phone numbers and message bodies.

## n8n receiving workflow

1. Create a POST Webhook node with its **Production URL**, **Header Auth**, **Raw Body**, and a response node. Save successful executions without request data, and prune failed executions on a short schedule. Restrict workflow editing to operators who may see all booking data.
2. Use the Crypto node's **Hmac / SHA256 / HEX** action on the exact raw body, with the platform webhook secret in Crypto credentials. Compare the resulting digest with `X-Cal-Signature-256` using a constant-time string comparison. Reject missing or invalid signatures before any database or HTTP node.
3. Parse the signed JSON. Require `createdAt` to match `X-Rondevu-Timestamp` and be within 24 hours; require a 64-character hex `X-Rondevu-Event-Id`. Reject malformed events. The ingress key is an additional first gate; it does not replace the HMAC check.
4. Persist the event ID in a dedicated n8n/PostgreSQL deduplication table with a unique index. Respond with 2xx only after validation and durable acceptance. An already accepted event must not send another message. Keep retryable failed jobs distinguishable from completed jobs.
5. Route all supported event types into the workflow's event log, but only `BOOKING_CREATED`, `BOOKING_REQUESTED`, `BOOKING_CANCELLED`, and `BOOKING_RESCHEDULED` may enter the WhatsApp branch. Do not interpolate notes, custom answers, private meeting links, or arbitrary webhook text into messages.
6. For a WhatsApp event, send `bookingUid = payload.uid` and `triggerEvent` to `POST /api/internal/whatsapp/eligibility`, with the eligibility bearer credential. Use only its returned recipients. Call it again immediately before a delayed retry so a revoked preference takes effect.
7. For each recipient, claim a deduplication key consisting of event ID and recipient role/normalized number hash in the same durable store. Send via Evolution API `POST /message/sendText/{instance}` with a credential-scoped `apikey`; mark the key sent only after Evolution acknowledges it. Retry transient failures with bounded backoff; send failures to an operator queue. Keep Evolution and n8n on a private network where possible.
8. Configure Evolution's inbound message webhook to a separate authenticated n8n workflow. On a `STOP`/`DUR` reply, normalize the sender to E.164 and call `POST /api/internal/whatsapp/opt-out` with the eligibility bearer credential. Ignore other inbound messages in the notification workflow.

The webhook event body is deliberately the existing **full** payload. It may contain personal notes and custom form answers; restrict access to n8n and disable long-lived execution data. The eligibility API returns only the current WhatsApp recipients and basic booking fields.
Guest consent is carried to a rescheduled booking only while the prior booking's consent has not been revoked; each delivery still calls the eligibility API for the new booking UID.

Successful rOndevu deliveries discard their encrypted replay body. Set a scheduled database retention job for failed deliveries after the operator retry window, for example seven days; keep status metadata separately only for the period required by your support process. Do not copy full webhook bodies into n8n logs or error messages. A `PROCESSING` delivery older than 15 minutes can be retried from the admin delivery screen after an interrupted worker.

## Deployment check

- Confirm a normal user cannot read, edit, delete, create, or test a platform webhook. Confirm an administrator can deactivate it immediately.
- Confirm private/loopback webhook URLs are rejected for personal webhooks, and that the configured platform URL alone is accepted for the platform webhook.
- Confirm unsigned, altered, expired, duplicate, and redirected requests never send messages.
- Confirm an attendee without an explicit checked preference, or a host who has disabled the preference, is excluded.
- Confirm delivery failure appears at `/settings/admin/webhook-deliveries`; retry a failed event and confirm the same event ID cannot create a second WhatsApp message.
- Run `n8n audit` and resolve unprotected webhook and unsafe-node findings before activation.

Evolution's WhatsApp Web/Baileys connection depends on an active linked-device session. Monitor its connection state and pause sending when disconnected. This transport does not provide the same operational guarantees as WhatsApp Cloud API.
